## Goal
People reading Draw Attention's WordPress.org page see a Changelog section that lists each release's customer-facing changes.

Focus of this PR: WordPress.org shows a changelog that stays current — a changelog label gate in CI and WordPress.org changelog headings in the readme only, nothing else.

Scope: The release job builds the public changelog only from pull requests labelled `bug`, `bugfix` or `feature` (`.github/config/changelog_configuration.json`), and nothing makes a pull request carry one, so unlabelled work never reaches the changelog. The job also pastes Markdown headings into `readme.txt`, which WordPress.org does not read as a Changelog section. This PR adds one step to the Static Code Analysis job in `ci.yml` that fails a pull request carrying none of the config's labels and no `no-changelog` label, and runs that workflow again when a label is added or removed. It rewrites the release job's readme step in `release.yml` to write `== Changelog ==` and `= version - date =` headings with one flat bullet list per version, for the latest ten versions, and converts the changelog section already in `readme.txt` the same way. `tests/packaging/check-build.sh` gains a check on the shipped readme's changelog headings. Two repo labels are created: `no-changelog` and `bugfix`. ⏩ Out: the entries missed so far, the heading conversion in `Gruntfile.js` that the copy step overwrites, `CHANGELOG.md`'s own format, and labelling Dependabot's pull requests automatically. Shape: one step and one trigger line in `ci.yml`, one rewritten step in `release.yml`, the changelog section of `readme.txt`, a few lines in one test script, plus this file.
Risk: every pull request is touched. Static Code Analysis is the one required check, so a pull request with no changelog label cannot merge, Dependabot's included, until someone adds a label. A label change now re-runs Static Code Analysis, formatter included. On WordPress.org the changelog moves out of the description into its own section. The group headings (Fixes, Features and Improvements) no longer show in the readme; `CHANGELOG.md` keeps them. Undo: revert this PR. The 1%: the release job's readme step. No pull request runs it, and it rewrites `readme.txt` on master directly.

## Definition of Done
- [ ] On a pull request with no changelog label, Static Code Analysis fails at the label step, and its message names the accepted labels.
- [ ] Adding `no-changelog` to that pull request re-runs Static Code Analysis with no new commit, and the label step passes.
- [ ] `tests/packaging/check-build.sh` passes on this branch's WordPress.org file set and fails on master's, naming the changelog headings.
- [ ] WordPress.org's readme parser, run on this branch's `readme.txt`, returns a `changelog` section that holds the entries and a description that no longer holds them.
- [ ] The release job's readme step, run in a clean copy of this branch, leaves `readme.txt` unchanged; run again with a new top entry in `CHANGELOG.md`, it puts that entry first under `== Changelog ==`.
- [ ] `grep -rn "# Changelog" .github readme.txt` finds nothing: no step writes or expects the old heading.
