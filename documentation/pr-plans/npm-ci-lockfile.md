## Goal
Whoever builds or releases Draw Attention gets the same npm dependency versions on every run, so a new upstream release can't change a build nobody touched.

Focus of this PR: CI and release builds use the same dependency versions every run — install npm dependencies from a committed lockfile only, nothing else.

Scope: `package.json` lists ten devDependencies, three of them set to `latest`, and `.gitignore` keeps `package-lock.json` out of the repo, so every `npm install` in a workflow resolves versions fresh. This PR commits `package-lock.json` (`lockfileVersion` 3, written by the npm that ships with Node 20), removes its `.gitignore` line, and switches the six project installs to `npm ci`: one in `ci.yml`, two in `tests.yml`, one in `plugin-check.yml`, two in `release.yml`. The global tool installs (`prettier`, `eslint`, `@wordpress/env`) stay as they are. ⏩ Out: adding a Node setup step to `ci.yml` or `release.yml`, upgrading any dependency, pinning the global tools, and the checkout-credential and permissions changes another open branch makes in `ci.yml` and `tests.yml`. Shape: one generated lockfile, one line removed from `.gitignore`, six one-line edits across four workflow files, plus this file.
Risk: every job that installs npm dependencies is touched: Static Code Analysis, both Tests jobs, the WordPress.org Plugin Check and the release job. `npm ci` stops when `package.json` and the lockfile disagree, so a dependency change now has to commit the regenerated lockfile with it. `npm ci` also stops when a checkout has no lockfile, and Static Code Analysis checks out the pull request's own branch, so once this is on master that job fails on every open pull request whose branch has not merged master yet. The three `latest` devDependencies stay at their locked versions until someone regenerates the lockfile. The shipped plugin does not change: `Gruntfile.js` already leaves `package-lock.json` out of the WordPress.org file set, and `tests/packaging/check-build.sh` already fails a build that contains it. Each release now commits the lockfile's version field too: `release.yml` runs `npm version`, which bumps `package.json` and `package-lock.json` together, before its `git add -A .`. Undo: revert this PR. The 1%: the release job. It is the only one of these jobs with no pull request trigger, and the only one where `npm version` rewrites the lockfile before `npm ci` reads it. It also uses the runner's own Node, as `ci.yml` does, so that npm must read `lockfileVersion` 3.

## Definition of Done
- [ ] `package-lock.json` is tracked with `lockfileVersion` 3, and `.gitignore` no longer lists it.
- [ ] `grep -rn "npm install" .github/workflows` lists only global tool installs: every project install is `npm ci`.
- [ ] Static Code Analysis, both Tests jobs and the WordPress.org Plugin Check pass on this branch, each installing with `npm ci`, and none of them changes `package-lock.json`.
- [ ] The WordPress.org file set built from this branch contains no `package-lock.json`: the Packaging job's `tests/packaging/check-build.sh` passes.
- [ ] In a clean copy of this branch, the release job's commands in order (`npm version patch --no-git-tag-version`, `npm ci`, `npx grunt increment-version`, `npx grunt wporg`) all succeed, and `package.json` and `package-lock.json` end on the same version.
